# Port scan detection: the Python protobuf bindings

`proto/ui.proto` carries a `PortScan` message, an `Alert.What.PORT_SCAN` value
and the `PORTSCAN_BLOCK`, `PORTSCAN_UNBLOCK` and `PORTSCAN_BLOCK_INFO`
notification actions. The Go bindings are generated at build time and need
nothing special. The Python ones are committed, and there are **two** sets of
them:

| Path | For | Generated with |
|---|---|---|
| `ui/opensnitch/proto/ui_pb2.py` | protobuf >= 4.0.0 | `protoc 3.21.12` |
| `ui/opensnitch/proto/pre3200/ui_pb2.py` | protobuf >= 3.6.0 and < 3.20.0 | `protoc 3.7.1` |

`ui/opensnitch/proto/__init__.py` picks between them at import time, on the
boundary `Version(proto_version) < Version("3.20.0")`. Any change to
`ui.proto` must regenerate both.

## Why the compiler version matters

Each generation of `protoc` emits a different flavour of Python, and the flavour
decides which runtimes can load the file:

* `protoc >= 3.20` emits the `builder`-based form. It needs a runtime of that
  generation or newer, which is exactly why `pre3200/` exists.
* `protoc >= 5` additionally emits a
  `_runtime_version.ValidateProtobufRuntimeVersion(...)` preamble, which makes
  the GUI refuse to start on an older runtime.
* `protoc 3.8` dropped the Python 2 compatibility shim and switched to
  `AddSerializedFile`. A file generated by 3.8 or later will **not** load on
  protobuf 3.6 or 3.7, so regenerating `pre3200/` with anything newer than
  3.7.x would quietly narrow the range the GUI claims to support.

So the modern set is generated with `protoc 3.21.12` and the legacy set with
`protoc 3.7.1`, each matching the flavour of the file it replaces: the
generated preamble stays byte-identical, and only the descriptors change.

The gRPC stubs (`ui_pb2_grpc.py`, `pre3200/ui_pb2_grpc.py`) only change when
a `service` or an `rpc` does; the port scan additions are messages and enum
values, so they leave the stubs as they are.

## Regenerating

```sh
cd proto

# modern set (protobuf >= 4.0.0), with a protoc of the 3.20-4.x generation
protoc -I. --python_out=../ui/opensnitch/proto/ ui.proto

# legacy set (protobuf >= 3.6.0, < 3.20.0), with protoc 3.7.x
protoc -I. --python_out=../ui/opensnitch/proto/pre3200/ ui.proto
```

`proto/Makefile` carries the first command as its `ui_pb2.py` target, via
`grpc_tools.protoc`; use whichever entry point matches the pinned toolchain.

## Checking them

There are three implementations of this message in the tree, the Go bindings
the daemon serialises with and the two Python generations, produced by three
different compilers. A disagreement between any two of them shows up as a GUI
that starts, connects, and silently never displays a scan. So they are checked
against each other rather than each against itself:

```sh
PYTHON_MODERN=python3 PYTHON_LEGACY=/path/to/python3.7 \
    proto/run_binding_check.sh
```

Each implementation writes the same fully populated alert and the others read
it back, and each Python generation must produce the same bytes as Go.
`PORTSCAN_REQUIRE_BOTH=1` turns "no legacy interpreter available" into a
failure instead of a skip, which is what CI uses.

To check one file on its own:

```sh
python3 proto/check_portscan_bindings.py \
        ui/opensnitch/proto/ui_pb2.py
```

The checker also pins the wire values `Alert.PORT_SCAN = 7`,
`PORTSCAN_BLOCK = 15`, `PORTSCAN_UNBLOCK = 16` and
`PORTSCAN_BLOCK_INFO = 17`: they are never repurposed, only added to.
